# Проверки перед публикацией и восстановление MR

Этот документ описывает проверки **целевого проекта**, которые запускает воркер. Это отдельный механизм от GitHub Actions, проверяющего сам AI-Developer; для него см. [CI_RUNBOOK.md](CI_RUNBOOK.md).

## Обязательные и необязательные проверки

`lint` и `tests` обязательны. Runner обрезает внешние пробелы команды. Если команда отсутствует или содержит только пробелы, результат — `failed`, дальнейшие команды не запускаются. Это действует и при построении конфигурации программно в обход parser/preflight.

`typecheck`, `build`, `security_scan`, `sast`, `coverage` и `visual_regression` остаются необязательными: если команда не задана, такой gate может иметь `skipped`. Когда команда задана, проверка должна успешно выполниться. Тайм-аут считается ошибкой независимо от exit code.

Проверки идут в прежнем порядке:

```text
typecheck → lint → tests → build → security_scan → sast → coverage → visual_regression
```

Ошибка останавливает дальнейшее выполнение gates. Успешным результатом не считаются пустой список, отсутствие или пропуск обязательного gate, дублированный ID, ошибка любого gate и пропуск настроенной команды. Ошибки команд по-прежнему передаются в ограниченный цикл исправлений Codex; по исчерпании бюджета задача завершается с ошибкой.

Если для проекта не существует команды lint/tests, настройте осмысленную проверку для его стека. Не заменяйте её `true` или заведомо успешной заглушкой ради обхода контроля: runner проверяет результат команды, но не способен доказать полезность самих тестов.

## Восстановление задачи с открытым MR

Наличие MR и committed diff **не является доказательством проверки текущего кода**. При восстановлении задачи `InternalWorkerOrchestrator`:

1. Переиспользует существующие изменения вместо повторной генерации реализации.
2. Запускает текущие quality gates и сохраняет новый validation record.
3. При ошибке применяет существующий лимит автоматических исправлений. Если проверки не пройдены, не делает публикацию и не переводит задачу в `review`.
4. После успешной проверки переиспользует MR без создания дубликата и сохраняет validation summary.

Уже существующий внешний MR при ошибке не удаляется и не закрывается: блокируются именно действия публикации и успешный статус со стороны воркера. Дальнейший merge должен быть защищён правилами целевого GitLab-проекта.

## Кеширование и границы гарантии

В этом варианте кеш по commit SHA **не реализован**: восстановленная задача проверяется заново даже при наличии старого успешного результата. Это сознательный выбор надёжности вместо ускорения и не требует миграций БД. Оптимизация потребует доказательства проверки, учитывающего HEAD, base revision, конфигурацию gates и состояние рабочего дерева.

Повторные проверки не обеспечивают атомарность против стороннего изменения checkout во время исполнения. Доступ к checkout должен быть изолирован; leases координируют только участвующих воркеров. Также это не заменяет независимое ревью, проверку реальности бага или production-проверки после деплоя.

Изменение не ослабляет [профили окружения процессов](EXECUTION_ENVIRONMENT.md), не меняет sandbox, зависимости или схему PostgreSQL.

## Проверка изменений

```bash
npm run typecheck
npx vitest run tests/reliableValidation.test.ts tests/qualityGates.test.ts tests/internalWorkerOrchestrator.test.ts
npm test
npm run test:smoke
npm run build
```

Регрессии охватывают пустые/пробельные команды, fail-fast, optional skips, некорректные наборы результатов, тайм-аут, успешное восстановление MR, падение актуальных проверок и изменение конфигурации после предыдущего успешного результата. Recovery-тесты исполняют локальные Node-команды, но GitLab и Codex заменены тестовыми адаптерами; реальные модели и production-сервисы не вызываются.
