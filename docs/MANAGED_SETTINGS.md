# Настройка подключений и проектов через интерфейс

## Статус и граница первой версии

Новый **опциональный** режим включается `MANAGED_SETTINGS_ENABLED=true`. Используется существующая Angular-консоль и внутренний PostgreSQL-трекер. Интерфейс запускается с нулём проектов. После подключения GitLab администратор добавляет репозиторий и включает его без перезапуска приложения. Режим env/fleet по умолчанию не изменён.

В этой версии доступны GitLab-подключения, замена токенов, проекты, ветка, lint/tests/build/typecheck, модель и тайм-аут Codex, лимит исправлений, пауза и отображение сохранённой/применённой версии. Это **не перенос всех настроек**: Telegram, Yandex bridge и Project Manager пока не подключаются к managed runtime; их нельзя одновременно включить в этом режиме. Массового импорта прежнего YAML и переноса старых идентификаторов проектов нет.

Первая установка предназначена для контролируемого пилота с одним worker. Дополнительные настройки и несколько исполнителей требуют отдельных эксплуатационных проверок. PostgreSQL advisory lock дополняет, но не заменяет существующие leases и ручное восстановление начатой работы.

## Быстрый локальный Docker-запуск

Из корня репозитория:

```bash
node scripts/init-managed-env.mjs https://gitlab.example.com
# Для GitLab.com: node scripts/init-managed-env.mjs https://gitlab.com

docker compose --env-file .env.managed -f compose.managed.yaml config
docker compose --env-file .env.managed -f compose.managed.yaml up --build
```

Генератор создаёт **новый**, не перезаписываемый `.env.managed`: случайные пароль БД, токен администратора и ключ шифрования. Он не печатает значения в stdout. Файл исключён из Git и Docker build context; на Unix запрашиваются права `0600`. На Windows дополнительно проверьте ACL. Команда `docker compose config` разворачивает переменные, поэтому её вывод содержит секреты: не публикуйте его.

Откройте `http://localhost:9464/tasks/settings`. Введите `TASK_TRACKER_SYSTEM_TOKEN` из `.env.managed` в форму входа. Токен хранится только в памяти вкладки, не в localStorage/sessionStorage/cookies или URL. После обновления вкладки потребуется повторный вход. Это bootstrap-доступ одного администратора, а не полноценная пользовательская система IAM.

`compose.managed.yaml` не требует checkout на хосте. Он поднимает отдельные PostgreSQL, workspace и Codex volumes. PostgreSQL не публикует порт, UI слушает на localhost хоста; автоматический рестарт выключен. Не используйте эту схему для открытого HTTP-доступа через Интернет. Для удалённого доступа нужен TLS и защищённый proxy.

При первом запуске managed backend применяет миграции до старта интерфейса. БД обязана быть доступна, даже если проектов пока нет. Не направляйте пилот на существующую production-БД без резервного копирования и отдельного согласованного rollout.

## Авторизация исполнителя

Codex остаётся серверным runtime, а не настройкой браузера. Укажите поддерживаемый текущим CLI API-key режим через `CODEX_API_KEY` либо авторизуйте отдельный том:

```bash
docker compose --env-file .env.managed -f compose.managed.yaml build worker
docker compose --env-file .env.managed -f compose.managed.yaml run --rm --entrypoint codex worker login --device-auth
docker compose --env-file .env.managed -f compose.managed.yaml run --rm --entrypoint codex worker login status
```

Не делите один OAuth `CODEX_HOME` с хостом или другим worker. При включении проекта проверяются локальная доступность CLI и auth status (каждая команда ограничена 15 секундами). Это **не реальный запрос к модели**, не проверка лимита подписки и не подтверждение, что заданная модель доступна. Платные вызовы при onboarding не выполняются.

## Порядок добавления проекта

1. В разделе «Подключения GitLab» выбрать разрешённый origin, ввести имя и токен. Проверка выполняет чтение GitLab API. Токен шифруется, UI получает только признак наличия credentials.
2. Нажать «Добавить проект», выбрать подключение и репозиторий из списка (есть пагинация). Название и default branch предлагаются из GitLab. Репозиторий существующего проекта не подменяется: для другого репозитория создайте новый проект.
3. Проверить ветку и команды. `npm test`/`npm run lint` — **примеры, не автоматическое определение стека**. Изменение команд равнозначно разрешению выполнить код на сервере; это действие только администратора.
4. Сохранить. Новый проект остаётся выключенным.
5. Нажать «Проверить и включить». Worker подготовит checkout и проверит GitLab, ветку и CLI на границе рабочего цикла. Состояние изменится с «Ожидает применения» на «Применено» либо «Ошибка проверки».
6. В создании задачи выбрать проект. `repositoryName`, `repoPathKey`, ветка и очередь подставляются системой; сервер повторно проверяет выбранный проект. Задачи остаются в привычном человеческом процессе приёмки и запуска.

Checkout находится только под `SETTINGS_WORKSPACE_ROOT/<project UUID>`. Не принимаются произвольные пути, symlink-подмена или другой remote существующего checkout. При первичном clone запрещены submodules, локальный file protocol, git hooks и редиректы. В процессе проверки **не выполняются** npm install, тесты и другие скрипты репозитория; существующие незакоммиченные изменения не сбрасываются.

Важно: runtime/toolchain и зависимости целевого проекта всё ещё должны быть доступны исполнителю. Сам факт клонирования не устанавливает Node/Go/Java или `node_modules`. Не включайте непроверенный репозиторий в исполнение, пока не подготовлено изолированное рабочее окружение.

## Сохранение, применение и текущие задачи

- PostgreSQL — источник истины в managed mode. `WORKER_CONFIG_FILE` одновременно запрещён; UI не редактирует `.env` и не обещает изменить инфраструктурные параметры.
- Настройки имеют общую ревизию и отдельную ревизию проекта. При конфликте изменений API возвращает `409`, а не перетирает чужую запись. В UI редактируемая форма сохраняет исходную ревизию.
- Новая конфигурация хранится отдельно от active. Проверка GitLab/ветки/checkout/CLI выполняется до активации. При неудаче прежняя active остаётся действующей; причина видна в карточке.
- Проверка настройки не запускает команды качества. Неверный test command или недоступная модель могут проявиться уже в задаче, даже если onboarding прошёл.
- На время запуска используется неизменяемый снимок. Несекретные параметры записываются в событие задачи и сохраняются при resume/review после рестарта. Новые задачи получают последнюю применённую версию. Токены не записываются в события задач; при последующем запуске берётся актуальное подключение.
- Пауза запрещает последующий dispatch после наблюдения worker изменения. Уже работающая задача не прерывается. При длительной задаче применение может ждать её завершения; это не «мгновенный hot swap».
- Применённая версия и время наблюдения видны отдельно для worker. Запись о worker может быть устаревшей при его остановке — смотрите timestamp.
- Ротация токена сначала проверяет аккаунт и доступ к активным проектам. Отказ не заменяет прежний токен. Проверка чтения не доказывает право push: права доступа GitLab и branch policies нужно проверить отдельно.

Ошибка применения нового проекта не должна блокировать уже работающий проект. Невозможность прочитать реестр блокирует dispatch: приложение не продолжает исполнение по догадке. Уже запущенный дочерний процесс отдельным механизмом этой фичи не убивается.

## Bootstrap-параметры и безопасность

| Параметр | Назначение |
| --- | --- |
| `MANAGED_SETTINGS_ENABLED=true` | Новый режим; без него прежний runtime |
| `TASK_TRACKER_DATABASE_URL` | PostgreSQL (в Compose устанавливается автоматически) |
| `SETTINGS_ENCRYPTION_KEY` | Канонический base64 для 32 случайных байт |
| `SETTINGS_GITLAB_ORIGINS` | Список разрешённых HTTPS origins через запятую |
| `SETTINGS_WORKSPACE_ROOT` | Абсолютный обычный каталог, без symlink-компонентов |
| `TASK_TRACKER_HUMAN_AUTH_MODE` | localhost / bearer / trusted_proxy |
| `TASK_TRACKER_SYSTEM_TOKEN` | Для bearer обязательно минимум 32 символа; использовать случайный |
| `SETTINGS_TRUSTED_PROXY_CONFIRMED=true` | Явное подтверждение изоляции backend при trusted_proxy |
| `CODEX_HOME`, `CODEX_API_KEY`, CLI-настройки | Авторизация и базовая настройка исполнителя |

При localhost auth обязательно loopback-bind. При trusted_proxy backend должен быть недоступен напрямую, proxy удаляет входящие identity headers и подставляет проверенные. Флаг подтверждения сам по себе не создаёт такую защиту.

Токены шифруются AES-256-GCM со случайным nonce и привязкой к ID подключения. Ключ не хранится в БД: сделайте защищённую резервную копию отдельно от PostgreSQL. **Не меняйте ключ простым редактированием env**: автоматического перешифрования нет. Потеря ключа означает невозможность прочитать старые credentials. Audit хранит автора, тип операции и ревизию без значений токенов.

`SETTINGS_*` и `MANAGED_*` запрещены в allowlists дочерних процессов. Это не заменяет filesystem/network sandbox: файлы секретов, HOME и права контейнера требуют отдельной изоляции. Конфигурация managed mode использует `workspace-write`, но это не доказательство безопасного исполнения произвольного чужого кода. Команды проверок выполняются текущим shell-механизмом, поэтому пилот — только для доверенных проектов в изолированном окружении.

## Хранилище и rollback

Миграция `0016_managed_settings.sql` добавляет `managed_settings`, `managed_settings_audit`, `managed_worker_settings`. Старые миграции и task schema не переписываются. Перед обновлением — backup. Для возврата к прежнему env/fleet режиму остановите managed worker и запустите прежнюю конфигурацию; не удаляйте новые таблицы и volumes ради отката приложения.

Существующие env/fleet проекты автоматически не импортируются. Не используйте произвольное переименование ID задач для переноса между режимами. Первый rollout лучше выполнять с отдельной пилотной БД.

## Проверки

```bash
npm run typecheck
npm test
npm run build
npm run web:typecheck
npm run web:test
npm run web:build
npm run web:e2e
# Отдельная тестовая PostgreSQL согласно POSTGRES_INTEGRATION_TESTS.md:
npm run test:postgres
```

Backend unit/API тесты не обращаются к реальному GitLab или модели. HTTP API проверяется настоящим локальным сервером и тестовым хранилищем. `tests/postgres/managed-settings.integration.ts` проверяет реальные миграции, persistence/CAS/locks/audit на одноразовой PostgreSQL; не подменяйте этот прогон in-memory тестами. Browser E2E использует mock API и не доказывает рабочий GitLab OAuth или успешный реальный clone.
