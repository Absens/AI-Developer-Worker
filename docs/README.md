# Документация AI Developer Worker

Этот раздел — точка входа для разработчиков и администраторов. Объяснения и инструкции приведены на русском языке; имена переменных, команд, API, типов и путей сохранены в исходном виде, чтобы их можно было найти в коде.

**Текущее состояние:** универсальный Node.js/TypeScript-воркер, который получает задачи из внутреннего трекера или Yandex Tracker, выполняет инженерную работу через Codex CLI, запускает проверки и создаёт GitLab MR. Исследование конкурентов Wildberries/Ozon **не входит в текущий `main`**: эта экспериментальная реализация сохранена в ветке [`archive/competitor-research-2026`](https://github.com/Absens/AI-Developer-Worker/tree/archive/competitor-research-2026).

## Безопасность и известные ограничения

- В шаблоне конфигурации `CODEX_SANDBOX=danger-full-access`. Это **не безопасный вариант по умолчанию** для запуска недоверенных задач в корпоративной среде; требуются изолированное окружение, ограничения прав и контроль секретов.
- Runtime использует раздельные [профили окружения](EXECUTION_ENVIRONMENT.md) для Codex, Git и проектных команд вместо наследования всех переменных worker. Это не закрывает доступ к файлам секретов, домашнему каталогу, сети и другим процессам: нужна отдельная изоляция.
- Готовый MR не означает, что задача прошла независимое AI-ревью, человеческую приёмку или была развёрнута в production.
- Стандартный `compose.yaml` использует bind mount локального checkout и `HOST_CODEX_HOME`. Он **не реализует** полностью автономное серверное развёртывание из целевого плана.
- Наличие тестов в репозитории не гарантирует их успешный запуск на вашей машине. Перед merge и развёртыванием запускайте проверки и фиксируйте результаты.

## Как поддерживать документацию

1. После изменения runtime, публичного API, переменной окружения или процедуры запуска обновите соответствующий документ одновременно с кодом.
2. Новые пояснения пишите на русском; технические идентификаторы и исполняемые примеры не переводите.
3. Используйте относительные ссылки внутри репозитория. Не добавляйте локальные пути вида `C:/Users/username/...` в Markdown-ссылки.
4. Для новой идеи создавайте датированный план в `docs/superpowers/`. Не подменяйте им актуальный runbook.
5. Проверяйте команды по `package.json` и `web/package.json`; не описывайте отсутствующие npm scripts или CI pipeline.
