# PostgreSQL integration CI — план реализации

> Выполнение: superpowers:executing-plans. Пользователь подтвердил следующий PR после обсуждения сценариев и границ.

**Цель:** обязательный CI job с PostgreSQL 16, проверяющий реальные миграции, конкурентные claims/leases и сохранение состояния после закрытия и создания новых соединений.
**Архитектура:** отдельный Vitest config и npm entrypoint; одноразовая схема на тест; независимые pg.Pool для воркеров; штатный migration runner и PostgresTaskTrackerClient. Без mock SQL.
**Стек:** существующие Node 22, TypeScript, Vitest, pg, GitHub Actions.
**Основание:** согласованный в переписке план: миграции, одна задача/два воркера, один checkout/две задачи, разные репозитории, истечение leases, переподключение. База: `028daae83441a207f70417d0e7b95585524c2756`.

## Ограничения

- Не менять production runtime, SQL миграции, зависимости, lockfiles, sandbox или права доступа.
- Только отдельная ветка и PR; main не сливать автоматически.
- Никаких production credentials, вызовов моделей или внешнего GitLab.
- Не называть создание нового клиента перезапуском процесса или fault-injection сети.
- Локальная среда исполнителя не имеет DNS-доступа к GitHub/npm и PostgreSQL; доказательства запуска получать из GitHub Actions.

## Решения

- Новый набор отделён от обычного `npm test`; отсутствие URL в `test:postgres` — ошибка, не skip.
- Принимаются только loopback URL к базе с суффиксом `_test`; корневой `.env` не загружается.
- В тестах схемы имеют случайный контролируемый префикс; никакие пользовательские схемы не удаляются.
- Отчёт Vitest должен содержать реальные успешные проверки без skipped/todo; отсутствие отчёта тоже ошибка.
- Два воркера используют разные pg.Pool/соединения, а не один pg.Client. Продвижение инъецированных часов используется только для детерминированной проверки TTL, без sleep.
- Обнаруженные ошибки runtime не скрывать ослаблением тестов; диагностировать отдельно, сохранить красный результат в PR при необходимости.

## Задачи

1. **RED:** `tests/postgresCiContract.test.ts` фиксирует отсутствие PostgreSQL service job, обязательной зависимости `CI required` и dedicated npm script. Открыть draft PR и увидеть ожидаемые failures.
2. **Набор тестов:** добавить изолированный fixture с pools, миграции и проверки реальной БД. Проверить очистку схемы/соединений и независимые backend PID.
3. **Fail-closed runner:** предусмотреть отказ при неправильном/отсутствующем URL, недоступной БД, пустом/пропущенном наборе; добавить unit tests защитного контракта.
4. **CI:** добавить PostgreSQL 16 service, healthcheck, dedicated command, включить job в `needs` и итоговую проверку.
5. **GREEN:** выполнить полный CI (backend, Angular, browser E2E, PostgreSQL), проверить результаты и diff; описать ограничения по-русски и подготовить PR к ревью.

## Критерии приёмки

Миграции из пустой схемы и повторный прогон; настоящий preflight схемы; конкурентное получение одной задачи одним воркером; сериализация одного checkout; независимость разных checkout; истечение и повторный claim; отказ старым полномочиям на новый lease; сохранение вопроса, validation/MR и leases после новых соединений. Все проверки должны исполняться в обязательном job, без тихого skip.
