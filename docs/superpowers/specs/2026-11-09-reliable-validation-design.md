# Надёжная валидация перед публикацией MR

## Основание

Продолжение согласованного плана CI → execution environment → reliable validation. CI (#17) и минимизация окружения (#18) уже в main. База этого изменения: `215a16b8508da839f0f7d23e3b03dcfc6ed65b28`.

## Цель

Не объявлять результат проверенным при отсутствии обязательных команд или только потому, что у ветки существует открытый MR. Изменение не добавляет самостоятельный merge/deploy и не меняет права исполнения.

## Контракт

- `lint` и `tests` обязательны. Отсутствующая или пробельная команда — failed, а не skipped.
- После ошибки следующие команды не исполняются. Не настроенные необязательные проверки по-прежнему могут быть skipped.
- Пустой набор результатов, отсутствие, пропуск или дублирование обязательной проверки, а также пропуск настроенной проверки не являются успехом.
- Тайм-аут не считается успехом даже при противоречивом exitCode=0 от runner.
- При восстановлении задачи с существующим MR проверяются текущие команды. Старый зелёный результат не является основанием пропустить проверки.
- Провал проверок не переводит задачу в review и не публикует результат. Сохраняются существующий цикл исправлений и его лимиты.
- MR переиспользуется без создания дубликата только после успешной валидации.

## Рассмотренные подходы

1. Кеш результатов по commit SHA, base revision, конфигурации и версии gates. Экономит повторные тесты, но требует надёжной инвалидации, хранения доказательства проверки и учёта незакоммиченного дерева.
2. Повторно проверять восстанавливаемые MR через существующий pipeline. Дороже по времени проверок, зато не требует миграций и устраняет доверие к устаревшим результатам.

На этом этапе выбран второй подход как консервативное инженерное решение исполнителя. SHA-кеш — отдельная оптимизация, не реализуется и не подразумевается в этом PR. Этот шаг не обеспечивает атомарность против стороннего изменения checkout во время тестов; изоляция checkout остаётся отдельной границей.

## Не входит

Миграции БД, обновление зависимостей, новый sandbox, project ACL, модельные вызовы в CI, деплой, перенос памяти, глобальный рефакторинг и кеширование валидации.

## Проверки

Регрессии в `tests/reliableValidation.test.ts` сначала запускаются на неизменённом runtime (RED), затем на исправленном (GREEN). Полный GitHub Actions проверяет backend, Angular и browser E2E. Модели и production-сервисы не вызываются. Восстановление MR проверяется с настоящими локальными командами, InMemoryTaskTracker и фиктивными Git/GitLab/Codex адаптерами.
