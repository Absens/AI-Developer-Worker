# Phase 8D - Frontend Production Hardening Plan

## Goal

Make the Angular console safe and practical for continuous self-hosted use.

This phase closes frontend production gaps: auth alignment, packaging, Docker
and Windows runbooks, E2E coverage, visual regression baseline, accessibility,
static asset caching, and old embedded task UI removal.

## What Is In Scope

- Align Angular UI behavior with backend auth modes:
  - trusted proxy;
  - bearer token;
  - localhost-only development.
- Role-aware navigation and disabled states.
- Confirm dialogs for destructive or high-impact commands.
- Static asset caching headers.
- Docker build integration for the Angular bundle.
- Local Windows/PowerShell runbook updates.
- E2E tests for critical workflows.
- Visual regression smoke path if the repo has a command configured.
- Accessibility baseline:
  - keyboard navigation;
  - focus management;
  - labels;
  - contrast sanity check.
- Responsive layout baseline.
- Error boundary and retry UX.
- Documented relationship between:
  - Angular task tracker console;
  - existing observability dashboard.
- Removal of the old embedded task UI route/code once Angular is the primary UI.

## What Is Out Of Scope

- Full enterprise SSO.
- Multi-tenant security.
- Replacing Prometheus/Grafana.
- Fully custom design system.
- Mobile-first feature parity for every operator workflow.

## Auth Alignment

Minimum behavior:

- anonymous mutation controls are never shown as usable;
- viewer role can read but cannot mutate;
- developer role can create/update/answer/resume/cancel allowed tasks;
- operator role can retry/hold operational states;
- admin role can see any admin-only controls introduced later;
- bearer mode has a documented reverse proxy or service-client flow; do not add
  a browser token entry field in Phase 8D;
- trusted proxy mode uses backend-provided role data where available;
- localhost mode is clearly marked as development-only.

The frontend must not be treated as the security boundary. Backend role checks
remain authoritative.

The frontend should use `GET /api/session` as the only bootstrap source for
current role, auth mode, paths, and capabilities. E2E tests must include at
least viewer, developer, and operator sessions.

## E2E Coverage

Add E2E tests against a test server with an in-memory tracker or a controlled
test adapter.

Use Playwright as the Phase 8 E2E tool. Put selectors on stable
`data-testid` attributes instead of depending on PrimeNG internal markup, CSS
classes, or translated text.

Critical flows:

- load queue;
- create draft task;
- create ready task;
- open task detail;
- preview agent context;
- answer and resume;
- retry failed task;
- approve proposal;
- reject proposal;
- open operations view.

Prefer stable data-test selectors over CSS or text-only selectors.

The E2E seed data should reuse the canonical fixture set from
`HUMAN_API_CONTRACT.md`.

## Static Asset Serving

Production static serving should:

- serve `index.html` with no-store or short cache;
- serve hashed JS/CSS assets with long cache when generated by Angular;
- return clear 404s for missing assets;
- support deep links such as `/tasks/task-123` by serving `index.html` for
  frontend routes;
- keep `/api/...`, `/metrics`, `/healthz`, and `/readyz` routed to backend
  handlers.

Cache behavior:

- `index.html` and frontend route fallbacks: `no-store` or a short cache;
- hashed JS/CSS/media assets: long cache with `immutable`;
- non-hashed assets under `/tasks/assets`: conservative cache unless the build
  proves they are content-hashed;
- missing assets: clear `404`, not the Angular index.

Route precedence tests are required for every reserved backend path.

## Packaging

The considered packaging paths are:

1. Build Angular inside Docker image.
2. Build Angular separately and copy artifacts into the runtime image.
3. Mount prebuilt Angular assets in self-hosted deployments.

The first production-ready path should be simple, reproducible, and friendly to
Windows developers.

Phase 8D decision: build Angular inside the Docker image by default. The
Dockerfile should:

- install backend dependencies with the existing root lockfile;
- install frontend dependencies from `web/package-lock.json`;
- run `npm run web:build`;
- copy `web/dist/task-tracker-console/browser` into the runtime image;
- set or document `TASK_TRACKER_UI_STATIC_DIR` for the copied artifact path.

Self-hosted deployments may still mount prebuilt assets, but that is a fallback
path and must not be the only documented production path.

## Visual And UX Baseline

Verify:

- desktop layout at common operations-console width;
- narrow layout for laptop/mobile widths;
- no overlapping text or controls;
- long task titles wrap safely;
- status tags and action buttons keep stable dimensions;
- dialogs fit viewport;
- loading states do not shift layout heavily;
- destructive actions are visually distinct but not visually noisy.

Do not add decorative backgrounds, hero sections, or marketing content.

Verification should include Playwright screenshots for at least:

- desktop operations width;
- laptop/narrow width;
- task detail with a long title;
- confirmation dialog with a long reason field;
- operations page with stale refresh error.

Visual regression can start as smoke screenshots checked for non-empty render,
no major overlap, and stable selectors. Full pixel baselines can be introduced
later if the team wants stricter visual change review.

## Implementation Order

1. Verify `HUMAN_API_CONTRACT.md` matches final session/auth/static behavior.
2. Add role-aware frontend auth state from `GET /api/session`.
3. Align action visibility and disabled states with backend roles.
4. Add confirm dialogs and reason capture for high-impact commands.
5. Harden static asset serving, cache headers, and deep-link routing.
6. Add Docker build packaging path for Angular assets.
7. Add Playwright E2E test environment and canonical seed data.
8. Add critical workflow E2E tests.
9. Add accessibility, responsive, and visual smoke fixes.
10. Update runbooks and README.
11. Remove old embedded task UI routing/code. If removal is temporarily blocked,
    document the exact blocker and prove the code is no longer reachable in
    tests.
12. Run verification commands.

## Tests

Add or update tests for:

- `GET /api/session` role/capability behavior in each auth mode used by the UI;
- static asset cache headers;
- deep links serve the Angular index;
- backend API routes are not swallowed by frontend route handling;
- missing static assets return 404 rather than `index.html`;
- viewer cannot trigger mutation controls in E2E flow;
- backend still rejects unauthorized mutations;
- critical E2E workflows;
- frontend build in Docker;
- old embedded task UI route/code is removed or unreachable.

- `HUMAN_API_CONTRACT.md` reflects final Phase 8 behavior.
- Angular console is documented as the primary human UI.
- Existing backend auth remains authoritative.
- Role-aware UI behavior matches backend role model.
- Bearer browser behavior is documented without adding in-app token storage.
- Docker/local runbooks explain frontend build and serving.
- Deep links work.
- Static assets are served with appropriate cache behavior.
- Critical workflows have E2E coverage.

  documented with the reason.
- Docker build path that includes frontend assets passes.

## Rollback

Use:

```env
TASK_TRACKER_UI_ENABLED=false
```

to disable the human UI. If packaging fails in a deployment, the worker and
internal tracker should keep running. UI failure must not block worker
execution unless the deployment explicitly treats UI startup as mandatory. To
return to the old embedded UI, roll back to a previous application version.
