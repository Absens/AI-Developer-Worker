## AI Developer Worker (Codex CLI + Yandex Tracker + GitLab)

Разработать автономный сервис AI-разработчика, который в одном Docker-контейнере циклически обрабатывает задачи из Yandex Tracker, вносит изменения в код через Codex CLI и создает Merge Request в GitLab.

Итог работы по задаче в рамках данного ТЗ: подготовленная ветка, созданный Merge Request и перевод задачи в статус review. Автоматический merge в базовую ветку не выполняется.

---

# Назначение сервиса

Сервис работает как один worker-процесс и обрабатывает не более одной задачи за цикл.

Сервис должен:

* получать задачи из Yandex Tracker по тегу `ai_dev`
* брать в работу задачу, доступную для автоматической обработки
* подготавливать git-ветку в локальном репозитории
* передавать контекст задачи в Codex CLI
* запускать проверки результата
* публиковать изменения в GitLab
* создавать Merge Request
* синхронизировать статус и служебные комментарии в Yandex Tracker

---

# Архитектурные решения

В рамках этого ТЗ используются следующие обязательные решения:

* `git` используется для `fetch`, `checkout`, `pull`, создания ветки, commit и push
* GitLab API используется для создания и проверки Merge Request
* worker работает с одним локальным клоном репозитория
* worker запускается в одном контейнере и не обрабатывает задачи параллельно
* все реальные статусы Yandex Tracker задаются через конфигурацию, а не хардкодятся в коде

---

# Основной цикл обработки

Контейнер после запуска выполняет бесконечный цикл:

1. Проверяет, есть ли незавершенная задача, ранее взятая этим же worker.
2. Если такая задача есть, пытается продолжить ее обработку.
3. Если незавершенной задачи нет, запрашивает список задач из Yandex Tracker по тегу `ai_dev`.
4. Отбирает только задачи, соответствующие логическому статусу `open`.
5. Выбирает одну задачу для обработки.
6. Переводит задачу в логический статус `in_progress`.
7. Добавляет служебный комментарий `AI STATUS:` о начале работы.
8. Синхронизирует локальный репозиторий с базовой веткой.
9. Создает или переиспользует рабочую ветку задачи.
10. Формирует prompt и передает задачу в Codex CLI через stdin.
11. Получает результат выполнения и проверяет, были ли изменения в репозитории.
12. Если изменения есть, запускает тесты и линтер.
13. Если проверки проходят, делает commit, push и создает Merge Request в GitLab.
14. Добавляет в Tracker комментарий со ссылкой на Merge Request.
15. Переводит задачу в логический статус `review`.
16. Если подходящей задачи нет, уходит в ожидание на `POLL_INTERVAL_MINUTES`.
17. После ожидания повторяет цикл.

Worker обязан работать идемпотентно: повторный запуск не должен приводить к созданию дублирующих веток, коммитов и Merge Request для одной и той же задачи.

---

# Правила выбора задачи

Источник задач: Yandex Tracker REST API.

Обязательные правила выбора:

* выбираются только задачи с тегом `ai_dev`
* выбираются только задачи, доступные для логического статуса `open`
* если подходящих задач несколько, выбирается одна задача с наиболее ранним `createdAt`; если поле отсутствует, используется `updatedAt`
* если задача уже помечена другим worker через служебный комментарий или внутренний идентификатор исполнителя, текущий worker ее не берет

---

# Логические статусы и маппинг

Сервис оперирует следующими логическими статусами:

* `open`
* `in_progress`
* `waiting_for_answer`
* `review`
* `failed`
* `done`

Требования:

* реальные статусы и переходы Yandex Tracker задаются через конфигурацию `TRACKER_STATUS_MAP`
* код worker не должен зависеть от конкретных русских или английских названий статусов очереди
* переходы между статусами выполняются только через логический слой маппинга

Минимально необходимые переходы:

* `open -> in_progress`
* `in_progress -> waiting_for_answer`
* `waiting_for_answer -> in_progress`
* `in_progress -> review`
* `in_progress -> failed`

---

# Взаимодействие с Yandex Tracker

Сервис должен уметь:

* искать задачи по тегу и статусу
* получать полное описание задачи
* читать комментарии задачи
* добавлять комментарии
* менять статус задачи через настроенный маппинг

Форматы служебных комментариев:

```text
AI STATUS:
worker={WORKER_ID}
state={logical_status}
details={text}
```

```text
AI QUESTION:
worker={WORKER_ID}
question={question_text}
```

```text
AI MR:
worker={WORKER_ID}
url={merge_request_url}
branch={branch_name}
```

Служебные комментарии используются для:

* трассировки этапов обработки
* восстановления после перезапуска контейнера
* исключения повторной обработки одной и той же задачи

---

# Взаимодействие с GitLab

Сервис работает с self-hosted GitLab.

Обязательные операции:

* определить проект по `GITLAB_PROJECT_ID`
* push рабочей ветки выполнять через `git`
* создавать Merge Request через GitLab API
* перед созданием Merge Request проверять, существует ли уже открытый Merge Request для этой ветки

Если Merge Request уже существует, сервис не создает новый, а использует существующий URL и продолжает синхронизацию статуса задачи.

---

# Работа с репозиторием

Рабочие директории контейнера:

* `/workspace` - корневая рабочая директория контейнера
* `/workspace/project` - локальный клон репозитория

Базовая ветка задается через `BASE_BRANCH`, значение по умолчанию: `main`.

Формат рабочей ветки:

```text
feature/ai-task-{tracker_id}
```

Пример:

```text
feature/ai-task-PROJECT-241
```

Перед выполнением задачи сервис обязан:

```bash
git fetch --all --prune
git checkout {BASE_BRANCH}
git pull origin {BASE_BRANCH}
git checkout feature/ai-task-{tracker_id} || git checkout -b feature/ai-task-{tracker_id}
```

Требования:

* если ветка для задачи уже существует локально, она должна быть переиспользована
* если ветка существует удаленно, сервис должен корректно продолжать работу с ней
* сервис не должен модифицировать базовую ветку напрямую

---

# Передача задачи в Codex CLI

Задача передается в Codex CLI через stdin.

В prompt должны быть включены:

* ключ задачи
* заголовок задачи
* описание задачи
* релевантные комментарии пользователя
* ранее заданные AI-вопросы и полученные ответы
* требования к анализу, плану, реализации и проверке результата

Минимальный шаблон prompt:

```text
Task: {tracker_id}
Title: {tracker_title}

Description:
{tracker_description}

Additional context:
{tracker_comments_and_answers}

Requirements:
1. Analyze the repository.
2. Create an implementation plan.
3. Implement the solution.
4. Run project tests.
5. Follow the existing architecture and coding style.
```

`CODEX_COMMAND` задается через конфигурацию и должен позволять неинтерактивный запуск Codex CLI внутри контейнера.

---

# Механизм вопросов и ожидания ответа

Если Codex CLI не может продолжить выполнение из-за нехватки входных данных, неоднозначности требований или отсутствия доступа к нужному бизнес-контексту, сервис должен:

1. Добавить комментарий формата `AI QUESTION:`.
2. Перевести задачу в логический статус `waiting_for_answer`.
3. Завершить текущую попытку обработки без commit и Merge Request.

При следующих циклах сервис должен:

1. Проверять задачи в логическом статусе `waiting_for_answer`, ранее помеченные этим же worker.
2. Искать комментарии, появившиеся после последнего комментария `AI QUESTION:`.
3. Если ответ найден, добавлять его в новый prompt для Codex CLI.
4. Возвращать задачу в логический статус `in_progress`.
5. Продолжать выполнение с существующей рабочей веткой.

Если новых комментариев нет, задача остается в `waiting_for_answer`, а worker переходит к следующему циклу ожидания.

---

# Проверка результата

После завершения работы Codex CLI сервис должен проверить, есть ли изменения в репозитории.

Если изменений нет:

* commit не создается
* push не выполняется
* в Tracker добавляется комментарий с причиной
* задача переводится в логический статус `failed`

Если изменения есть, сервис обязан:

1. Запустить тесты проекта.
2. Если тесты прошли, запустить линтер.
3. Если проверки упали, передать ошибки обратно в Codex CLI для автоматической попытки исправления.
4. Повторять цикл исправления не более `MAX_FIX_ATTEMPTS`.

Если после исчерпания `MAX_FIX_ATTEMPTS` тесты или линтер не проходят:

* задача переводится в логический статус `failed`
* в Tracker добавляется комментарий с краткой диагностикой
* Merge Request не создается

---

# Commit и Merge Request

Формат commit message:

```text
feat: implement {tracker_id}
```

Формат заголовка Merge Request:

```text
[AI] {tracker_id} implementation
```

После успешных проверок сервис обязан:

1. Создать commit.
2. Выполнить push рабочей ветки.
3. Создать Merge Request в целевую ветку `BASE_BRANCH`.
4. Добавить комментарий `AI MR:` со ссылкой на Merge Request.
5. Перевести задачу в логический статус `review`.

---

# Сбой и восстановление

Сервис должен корректно восстанавливаться после перезапуска контейнера или временных ошибок внешних API.

Обязательные требования:

* при старте worker определяет незавершенные задачи, ранее взятые этим же `WORKER_ID`
* если по задаче уже существует рабочая ветка, она должна быть переиспользована
* если по задаче уже существует открытый Merge Request, повторный Merge Request не создается
* если вызов Yandex Tracker API или GitLab API завершился временной ошибкой, задача не должна считаться завершенной
* все критические ошибки логируются в stdout/stderr контейнера и отражаются в служебном комментарии Tracker, если это возможно

# Безопасность

Контейнер должен иметь доступ только к:

* GitLab репозиторию и GitLab API
* Yandex Tracker API

Запрещен доступ к:

* production-базам данных
* runtime-секретам других систем
* внутренней инфраструктуре, не требуемой для работы worker

Сервис не должен использовать никакие привилегии, не необходимые для чтения задач, push веток и создания Merge Request.

---

# Критерии приемки

Решение считается соответствующим ТЗ, если выполняются все сценарии:

1. При наличии подходящей задачи worker переводит ее в `in_progress`, создает ветку, вносит изменения, проходит проверки, создает Merge Request и переводит задачу в `review`.
2. При отсутствии подходящих задач worker не делает побочных действий и уходит в ожидание на заданный интервал.
3. Если для продолжения работы нужен ответ человека, worker добавляет `AI QUESTION:`, переводит задачу в `waiting_for_answer` и после получения комментария продолжает работу в той же ветке.
4. Если тесты или линтер не проходят после допустимого числа попыток исправления, задача переводится в `failed`, а Merge Request не создается.
5. После перезапуска контейнера worker не создает дублирующие ветки, commit и Merge Request для уже обрабатываемой задачи.
6. При временной недоступности Yandex Tracker API или GitLab API worker не теряет состояние обработки и корректно повторяет работу в следующем цикле.

# Ограничения версии

В рамках данного ТЗ:

* не требуется параллельная обработка задач
* не требуется автоматический merge Merge Request
* не требуется работа более чем с одним репозиторием
* целевой тип проекта для первичной эксплуатации: фронтенд-приложение на Angular
